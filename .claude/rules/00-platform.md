# 00 平台规则（唯一真源）

> 本文件是本平台的**规则唯一真源**。脚本里的表（`plat/rules_data.py`）与人读的说明
> （`使用手册.md`）都指向这里；**同一规则不写第二遍**。
> 增加/修改规则 = 先改本文件，再改 `rules_data.py`，再用 `plat gate` 验证。

---

## 1. 平台是什么，不是什么

- **是**：把「需求→设计→制造→测试→发布」这 8 个工程串成一条可追溯、可检查、可度量的流水线。
- **不是**：替人做决定的东西。**AI 出初稿，人拍板**——这条不因技术进步而改变。
- **不含业务**：平台核心里不出现任何客户名、画面名、业务字段。案例全部在 `cases/` 下。

## 2. 八工程（阶段与产出的 ID 类型）

| # | 工程 | 命令 | 产出 ID | 成果物目录 |
|---|---|---|---|---|
| 1 | 要件理解（含需求取込） | `/requirements` | R, Q, ASM, ISS | `requirements/` |
| 2 | 基本設計 | `/basic-design` | F, I | `designs/basic/` |
| 3 | 詳細設計 | `/detail-design` | D, L, E | `designs/detail/` |
| 4 | フレームワーク・環境構築 | `/framework` | （管理文書 TECH_STACK / COMPONENTS） | `framework/` |
| 5 | 製造（コーディング） | `/coding` | （源码 + 管理文書 TRACEABILITY） | `src/` |
| 6 | 単体テスト | `/unit-test` | TC | `tests/unit/` |
| 7 | 結合・総合テスト | `/integration-test` | IT | `tests/integration/` |
| 8 | リリース・運用保守 | `/release` | REL | `release/` |

**工程 1 内含两个步骤**：①取込（把 docx/xlsx/pdf/口头 归一成 `raw/raw_requirements.md`，带来源锚点）
②要件结构化。**对外仍算 8 个工程。**

## 3. ID 规则（红线）

- 格式：`<类型码>-<3 位序号>`，例 `R-101`、`TC-115`。类型码见 §2 与 `rules_data.ID_TYPES`。
- **号段制**：每个模块由台账分配一个号段基数（100 → `101..199`，200 → `201..299`）。
  号段用于区分**同一案件下的不同模块**——看到 `1xx` 就知道是哪个模块。
- **唯一发号口**：`python -m plat ids alloc`。**手写 ID、猜号、跳号、复用**一律禁止。
- 类型码之外的新类型，必须先改本文件与 `rules_data.py`，否则 `plat gate` 的 G1 判 FAIL。
- 跨模块引用写 `<模块>.<ID>`（例 `ModuleB.F-201`），只在追溯表里使用。

## 4. 状态机与人工卡点

```
draft ──▶ reviewed ──▶ confirmed ──▶ frozen ──▶ (終端)
  └──────────┴────────────┴──────────┴──────▶ deprecated
```

- **成果物出来一律是 `draft`**。`draft` 不得进入下一工程。
- **只有 `confirmed` / `frozen` 才算「已承认」**，下一工程才允许开始。
- **承认是人的行为**：`/approve` 必写 `approved_by`（**人的标识符**）与 `approved_at`。
  **AI 不得自己写承认栏**——写了自己也就是自己批准自己。
- **11 个 skill 全部设 `disable-model-invocation: true`**：AI 不能自己进入下一阶段，
  必须人敲命令。这是机制，不是约定。
- **阻塞项**：`ISS` の `block: true` 未解决时，不得进入下一工程。
- **承認の瞬間に「初稿→承認版」の修正量を記録する**（`registry/adoption.yaml`）。これは
  「採用率」の実測値であり、**人の修正率ではない**（人が手で直したのか、人の指示で AI が直したのかは
  区別できない）。修正理由は任意で書ける（`plat adopt note`）。
  **理由が溜まると「AI がどの種類で外すか」を言えるようになる** — それが `knowledge/traps.md` の材料になる。

## 5. 成果物形态（两种，不要混）

| 扩展名 | 结构 | 用途 |
|---|---|---|
| `.yaml` | **单文档**。开头可有 1 个 `---`，**绝不许有第二个** | 机读源（台账式成果物） |
| `.md` | `---` 包住 front-matter，后面是正文 | 人读源（设计书、手册、报告） |

**必填字段（12 项）**：`id` `type` `title` `status` `version` `related_ids` `owner`
`created_at` `updated_at` `sensitivity`（`.yaml`；`.md` 同）。

- **位置不在字段里**：`case` / `module` / `stage` 一律由**路径**决定。同一事实不写两处。
- `sensitivity` ∈ `public` / `internal` / `confidential`。
- `related_ids` 是追溯的载体。**不写 `related_ids` 的成果物等于断链。**
- **集約ファイル**（1 ファイルに複数 ID を収める場合）は、front の `id` に
  **そのファイルに含まれる最小の ID** を書く。勝手な ID を立てない。G3 が検査する。
- **`ISS` の `block: true` は本当に止める。** `blocks_stage` に書いた工程は、
  その ISS が `confirmed`/`frozen` になるまで着手できない（G4）。**解くのは人。**

## 6. 六道门（一条命令跑完）

| 门 | 查什么 | 失败意味着 |
|---|---|---|
| G1 | ID 合法性（野号、跳号、复用、废号引用） | 台账被绕过 |
| G2 | 追跡閉ループ（每条 R 能到 TC/IT；每个 ID 都能从 R 追溯） | 断链 |
| G3 | 成果物格式（必填字段、状态值、放置位置与类型相符） | 机械可读性被破坏 |
| G4 | **人工卡点**（上流未承认，下流成果物不得存在） | 跳过评审 |
| G5 | 文書一貫性（键名 snake_case、管理文档已登记、手册里的命令真实存在） | 文档与实现脱节 |
| G6 | 機密ゼロヒット（见 `01-security.md`） | 泄露风险 |

`python -m plat gate` → 6 个 PASS 才准提交。**告警（WARN）不阻断，错误（ERROR）阻断。**

## 7. 命名

- **定义层**（`.yaml` / `.py` / 台账 / front-matter 键）：`snake_case`。
- **接口层**（`.ts` / `.vue` 的变量与方法）：`camelCase`。
- 文件名：成果物用 `<类型>-<通称>.<ext>`，源码用工程约定的命名。**混写由 G5 拦。**

## 8. 双形态与媒体

- **机读源是唯一真源**；人看的视图**必须由它生成**，**生成物不得手改**（下次生成会覆盖）。
- `.md` = 日文；人看的视图 = `<同名>.zh.html`（**中文**，外框也中文）。
  **不生成日文 `.html`**；`.zh.md` 用完即删。
- 各成果物の**人読版**は `plat md` が `readable/` に生成する（YAML が正）。
  `readable/*.md` と `*.zh.html` は**生成物**で、手で編集しない。
- 对外的正式版（Excel / Word）由 `plat export` 生成，放 `export/`（不入库）。
- **中文视图里不翻译实现值**（画面文言、项目名、ID）。译了就等于改规格。

## 9. 提交与追溯

commit 只用 7 种：`req` / `design` / `feat` / `test` / `fix` / `rel` / `chore`。本文末尾必须三行：

```
Trace: R-101->F-042->TC-003
AI: <skill 或 manual>@<ver>
Review: <人的标识符>
```

`Review:` 写**人**，不写 AI。这是「人拍板」的机器可读凭据。

## 10. 変化と進化

- **承認済みの設計を、設計を直さずにコードだけ直す**ことを禁ずる。変更は必ず上流から入れ、
  `/change` で影響面を出し、**戻す起点工程は人が決める**。
- **踩坑は資産**：バグ・指摘・門番 FAIL は `knowledge/traps.md` に 1 行残す →
  再発するなら本ファイルに 1 条足す → 機械で捕まえられるなら `plat gate` に 1 条足す。
- **門番は増やしてよいが、減らしてはならない**（検査の穴は事故の入口）。

## 11. 禁止事項（要約）

1. 手書き ID・野号・号の再利用
2. 承認欄を AI が書くこと
3. `confirmed` でない成果物で次の工程へ進むこと
4. `.yaml` に 2 つ目の `---` を書くこと（パーサが壊れる）
5. 生成物（`.zh.html` / `export/**`）を直接編集すること
6. 未マスクの機密を成果物・対外物へ書くこと
7. `plat gate` を通さないコミット

## 12. 実行体（agent）の共通契約

工程を実行する agent は、**すべてこの契約に従う**。各 agent ファイルはここを指すだけで、同じことを書き直さない。

**必読順**：本ファイル `00-platform.md` → `01-security.md` → 担当工程の `SKILL.md` → `references/schema.md` → 上流成果物。

**できること**：成果物を書く（`Write` / `Edit`）／`plat` で発番・検査・集計する。
**できないこと**：
1. **承認欄を書く**（`approved_by` / `approved_at`）。承認は人。
2. **上流成果物を書き換える**。矛盾を見つけたら**止まって報告**する。
3. **推測で空欄を埋める**。「たぶんこう」は書かない。書けないものは `null` にして未確定として報告する。
4. **ID を手で書く**。必ず `plat ids alloc`。
5. **門番を回避する**。`plat gate` が FAIL したら直す、ではなく**原因を報告して止まる**。

**停止条件**（どれか満たしたら作業を止めて人に返す）
- 上流工程が `confirmed` でない
- 仕様に矛盾がある／決めないと先へ進めない点がある
- 機密らしき値が出てきた（`01-security.md` §2）
- 設計に無い実装が必要になった

**報告フォーマット（15 行以内）**
```
1. やったこと：<1 行>
2. 産出：<ファイルパス>（<行数 or 件数>）
3. 統計：<ID 種別ごとの件数>
4. 門番：<plat gate の生出力 1 行>
5. 未確定：<人に決めてほしいこと。無ければ「無し」>
6. 停止理由：<止まったなら。無ければ「無し」>
```

**報告で守ること**：実測値（コマンドの生出力）を添える。「確認しました」「問題ありません」だけの報告は**報告ではない**。
